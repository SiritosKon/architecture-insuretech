# Task1. Обоснование технологической архитектуры (to-be)

## 1. Стратегия масштабирования и отказоустойчивости

**Решение: основной путь — горизонтальное масштабирование stateless-сервисов; вертикальное — вспомогательно, только для узлов БД. Обязательно — несколько зон доступности (AZ).**

- **Почему горизонтальное, а не вертикальное.** Вертикальное масштабирование (наращивание CPU/RAM одной ВМ) имеет потолок, требует простоя на ресайз и не устраняет single point of failure — то есть не помогает достичь 99.9%. Горизонтальное добавление реплик  даёт линейный рост пропускной способности под пик рекламной кампании и устойчивость к отказу отдельных реплик.
- **Где вертикальное уместно.** Узлы PostgreSQL (запись идёт в один primary) масштабируются в первую очередь вертикально + добавлением реплик для чтения. При 50 GB данных этого достаточно.
- **Зачем нужны дополнительные зоны доступности.** Текущий кластер и БД развёрнуты в одной зоне — это делает всю площадку единой точкой отказа: авария зоны = полный простой, что несовместимо с 99.9%. Поэтому переходим на регион с тремя зонами доступности (AZ-A/B/C) и схемой active-active: сервисы работают одновременно во всех зонах.

## 2. Развёртывание в нескольких зонах доступности

### a. Конфигурация Kubernetes — единый растянутый кластер

**Решение: один растянутый региональный кластер (Managed Service for Kubernetes), а не независимые кластеры на каждой площадке.**

Обоснование выбора:
- Зоны доступности находятся внутри одного региона → низкая latency между ними, растянутый кластер работает без штрафа на межзонных вызовах.
- Региональный control plane реплицируется по 3 AZ (мастера + кворум etcd) — отказ одной зоны не выводит из строя управление кластером.
- Zone-aware планирование: `topologySpreadConstraints` + `podAntiAffinity` равномерно раскладывают реплики по зонам, поэтому отказ зоны снижает мощность, но не роняет сервис.
- Проще эксплуатация: один кластер, один слой конфигурации, одинаковое поведение во всех зонах.

Почему не независимые кластеры на площадку: такой подход оправдан для мульти-регионального DR (высокая межплощадочная latency, изоляция), но добавляет GitOps-синхронизацию, дублирование конфигураций и сложность маршрутизации без выгоды внутри одного региона.

### b. Балансировка нагрузки и health checks

Путь трафика: **Cloud DNS → Application Load Balancer → ingress-nginx в кластере → сервисы**.

- **Cloud DNS** маршрутизирует пользователя на ближайшую точку и выполняет health-check-based failover на уровне DNS.
- **Application Load Balancer** распределяет запросы между backend-группами во всех зонах, отсекая нездоровые таргеты по health check.
- **B2B-трафик** идёт через **API Gateway** с per-partner rate limiting и далее на те же сервисы.
- **Cloud CDN** отдаёт статику с ближайшую "точку присутствия".

Health checks (проверки здоровья) на всех уровнях:
- ALB → target-group HTTP-проверка `/health`;
- Kubernetes `liveness`/`readiness` probes на каждом Deployment;
- БД — Patroni REST health + проверки HAProxy;
- Cloud DNS — health-check эндпоинтов для DNS-failover.

### c. Фейловер-стратегия (уровень «клиент ↔ приложение»)

**Решение: active-active по зонам доступности с автоматическим фейловером на здоровые AZ.**

- Сервисы работают одновременно во всех трёх AZ. При отказе зоны ALB перестаёт получать успешные health check от её таргетов и в течение секунд перенаправляет трафик на здоровые зоны; Cloud DNS дублирует это на DNS-уровне.
- Клиентские запросы к идемпотентным операциям безопасно повторяются (retry на клиенте/шлюзе).
- Автоматический фейловер укладывается в **RTO 45 мин** с большим запасом и обеспечивает целевые 99.9%.
- Для катастрофы уровня региона предусмотрен вариант расширения на второй регион с async-репликой БД (гео-DR).

### 2d. Конфигурация базы данных (RTO 45 мин / RPO 15 мин)

**Решение: кластер PostgreSQL под управлением Patroni + etcd (DCS), streaming replication, бэкапы в объектное хранилище с PITR.**

- **Фреймворк кластера — Patroni** поверх etcd как distributed configuration store: выбор лидера и автоматический фейловер.
- **Топология:** Primary (AZ-A, запись) + Sync Standby (AZ-B) + Async Standby (AZ-C, реплика для чтения / DR). Перед БД — **HAProxy + PgBouncer**: запись → лидер, чтение → реплики, пул соединений.
- **Как обеспечиваем RPO 15 мин:**
  - синхронная реплика даёт **RPO ≈ 0** по закоммиченным транзакциям (транзакция подтверждается только после записи на sync-standby);
  - непрерывный **WAL-архив** в Object Storage (pgBackRest / WAL-G) с интервалом < 15 мин обеспечивает **RPO ≤ 15 мин** даже при потере всего кластера.
- **Как обеспечиваем RTO 45 мин:** автоматический фейловер Patroni переключает лидера за ~30–60 c; при необходимости — восстановление из бэкапа. Оба сценария укладываются в 45 мин.
- **Резервное копирование:** pgBackRest — ежедневный full + инкременты + WAL-архив, Point-in-Time Recovery; копии в объектном хранилище, при гео-DR — cross-region.

## 3. Шардирование базы данных

**Решение: шардирование НЕ применяем.**

- Объём данных — 50 GB — мал и помещается на одном узле; шардирование не даёт выигрыша.
- Нагрузку на чтение закрываем read-репликами + PgBouncer, нагрузку на запись — вертикальным масштабированием primary.
- Шардирование добавило бы существенную сложность (роутинг, кросс-шардовые запросы, ребалансировка) без реальной выгоды при таком объёме. Возвращаемся к вопросу только при кратном росте объёма данных.

## Как решения закрывают исходные боли

- **Медленные страницы под нагрузкой** — горизонтальное масштабирование с HPA + CDN для статики.
- **Нарушение SLA из-за партнёра (250 RPS вместо 20)** — API Gateway с per-partner rate limiting (20 RPS по SLA) + circuit breaker: один партнёр больше не «съедает» ресурсы остальных.
- **Одинаковый latency по регионам РФ** — Cloud CDN (ближайший PoP) + GeoDNS; динамика обслуживается из региона ru-central1.
- **Падения и медленная реакция** — multi-AZ active-active + автоматический фейловер, а также Monitoring & Alerting (Prometheus + Grafana + Alertmanager, оповещение on-call): о сбоях узнаёт команда, а не пользователи.
